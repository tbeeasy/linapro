# LinaPro 提交整理

把混在一起的工作区改动整理成「哪几个提交、每个提交放什么、提交信息怎么写、命令怎么敲」。
本技能只产出方案与命令，执行提交需要用户明确授权。

`lina-community-commit-push-and-pr`负责提交后的`rebase`、推送与`PR`流程；本技能只负责提交前的分组与信息起草，两者不重复。

## 核心规则

1. **范围按主题判定，不按窗口判定。** 判据是「是否属于当前这件事」，不是「是否被本窗口碰过」。
   任务跨窗口、跨上下文压缩是常态；把窗口当范围会让早先窗口做的改动漏掉。
   实测反例：某插件功能在窗口 A 改了配置模板与`go.work`，窗口 B 才提交，按窗口取范围会漏掉父仓库全部改动。
2. 反过来，同一窗口里混着的**其它任务**改动必须排除。窗口范围既会漏、也会多，两头都要防。
3. **仓库边界以当前仓库根为上限。** 「全仓 / 全局 / 整个仓库」指当前仓库根（`E:\project\linapro`）
   加上它的子仓库 `apps/lina-plugins`，到此为止。父目录、兄弟目录里的其它 git 仓库与本次提交
   无关，不列、不扫、不报告。用户说「扫描全局未提交的仓库」时，要扫的是**这两个仓库各自的未提交内容**，
   不是磁盘上所有 git 仓库；用`find`/`ls`遍历上级目录属于越界。
4. 范围确定后收集文件级证据。只看`git diff`会漏掉未跟踪文件，必须叠加`git status`与`ls-files --others`。
5. 父仓库与子仓库都要取，不能因为「改动落在子仓库」就跳过父仓库的指针、注册与配置。
6. `apps/lina-plugins`是独立子仓库：其内文件的提交发生在子仓库，父仓库提交的是指针（`gitlink`）。
   跨两仓的一次功能改动**至少两次提交**，无法合并。
7. 提交顺序固定：子仓库 → 父仓库。指针提交必须先于父仓库中任何引用插件路径的改动
   （例如`go.work`），否则中间提交上`go build`会因模块不存在而失败。
8. 提交信息用中文，格式`type(scope): 标题`，正文拆成多个`-m`段。
9. 命令必须内联`-m`，一条命令即可粘贴执行，不要让用户手抄提交信息。
10. 未获明确授权，只输出信息与命令，不执行`git commit`、`git push`。
11. 发现与本次主题无关的改动（尤其真实密钥、运行时日志），报告并给出处置建议，不擅自回退。
12. **拆分依据只能是「历史上真实存在过的状态」，不能是工作区的操作痕迹。** 暂存区里躺着的
    中间快照、某次`git add`留下的边界，都不是提交理由——除非那恰好对应一个发布过的版本或
    合并上线过的分支。把一个从未提交过、未曾上线的新插件按「基础版 / 后续功能」拆两笔，
    等于伪造一段它先上线过基础版的历史，只会误导后来看日志的人。**新模块首次入库就整体一笔。**
13. **提交信息写给看日志的人，不是写给 reviewer 的 PR 描述。** 标题 + 一两段「为什么」即可；
    逐条罗列的文件级实现细节、字段清单、错误码、测试用例名一律不要进提交信息——那些在 diff 里。

## 步骤 1：确定范围

按「这件事是什么」划定范围，再用文件证据核对。四种取证线索，**必须合起来用**，只用任一条都会漏：

| 线索 | 手段 | 补什么缺口 |
|---|---|---|
| 任务主题 | 本次对话与已记录的变更名（如`openspec/changes/<name>/`） | 跨窗口的任务主线 |
| 变更文档 | 读`tasks.md`里「修改文件」类的记录 | 早先窗口改过、此刻没在对话里的文件 |
| 路径归属 | 按插件 / 模块路径整体取 | 同主题的零散改动 |
| 工作区扫描 | `git status --short`全量列出，再按主题筛选 | 未跟踪文件、遗漏项 |

默认形态：

| 用户说 | 范围 |
|---|---|
| 「整理提交信息」（默认） | 当前任务主题涉及的全部文件，跨窗口、跨两仓 |
| 「整理 linapro-lark-push」 | 该插件/模块路径，加上它在父仓库的注册与配置 |
| 「整理整仓」「扫描全仓 / 全局未提交」 | 本仓 + `apps/lina-plugins` 的全部未提交改动，不筛主题；**不越过仓库根** |

「全仓」「全局」都止于当前仓库根：别的项目仓库（`E:\project` 下的其它目录）不在范围内，
即使用户用了「全局」二字也不扩过去。若用户确实想同时整理另一个仓库，他会点名那个路径。

任务边界不清（例如同时有两个 OpenSpec 变更在推进）时，先列候选清单请用户确认，不要猜。

父仓库：

```powershell
git status --short
git ls-files --others --exclude-standard
```

子模块——`git status`显示`m apps/lina-plugins`时，禁止把该路径整体当成一个改动：

```powershell
git -C apps/lina-plugins status --short
git -C apps/lina-plugins ls-files --others --exclude-standard
```

`?? path/`形式的未跟踪目录必须展开成文件清单，才能判断里面混了什么：

```powershell
git ls-files --others --exclude-standard -- <path>
```

范围确认后，向用户复述三件事再往下走：本次要提交的文件清单（父仓库与子仓库分开列）、被排除的无关改动（只报名字）、不确定归属的文件（请用户裁决）。

**只在仓库根执行上面的命令，不要向上遍历目录找别的仓库。** 判断「还有没有漏掉的仓库」时，
检查的是本仓的子仓库登记（`git submodule status`）与工作区内嵌套的`.git`，不是父目录。
`E:\project` 下的兄弟仓库属于别人的工作区，其未提交状态与本仓提交无关。

若上下文已压缩、无法还原任务起点：用变更文档与主题关键词反查（`git log`、`git status`、`openspec/changes/`），仍不确定就把候选清单交用户勾选，**不要**默认按全量走，也**不要**默认按残留的窗口记忆走。

## 步骤 2：识别噪声

按下表逐项检查，发现问题先报告：

| 检查项 | 检查方式 | 处置 |
|---|---|---|
| 运行时日志被带走 | `git -C apps/lina-plugins check-ignore -v --no-index <file>` | 提交前删除或补`.gitignore` |
| 配置模板里的真实密钥 | 对比`git show HEAD:<file>`中的占位符 | 还原为占位符 |
| 单文件混入多个主题 | `git diff -U3 <file>`看`@@`的 hunk 数与内容 | hunk 小用`git add -p`；hunk 巨大则手工编辑 |
| 子仓库已有暂存内容 | `git -C apps/lina-plugins status --short`首列`A`/`M` | 提交时用`-- <path>`限定范围 |

判断「无关」前先确认用户意图：用户可能本来就要改（例如同时整理配置模板）。只报告事实，不臆测。

## 步骤 3：分组与排序

1. 一次提交 = 一个能独立复述的意图。
2. 同一意图的父仓库指针、模块注册、配置段**合并为一次提交**，不要拆成「指针」和「注册」两笔——读者得在两笔里拼完整故事。
3. **`openspec/changes/` 不提交。** 活动变更目录不纳入任何提交方案，归档时也不为它单独成笔——
   它是开发过程的草稿区，不是仓库产物。用户在步骤 1 复述范围时要明确说「`openspec/changes/` 已排除」。
   历史里若有误提交的变更目录，不要提议清理（`git rm --cached`），除非用户主动要求。
4. 排序：子仓库 → 父仓库（指针 + 注册 + 配置）→ 其它文档。
5. **「子仓库先于父仓库」只约束指针提交，不是全局铁律。** 该规则的作用是保证打指针时子仓库 SHA 已存在，
   派生出两条推论：
   - **父仓库里「插件消费的宿主能力」必须先于插件提交。** 例如插件页面调用了宿主组件的新 prop、
     宿主注册表的新钩子、`RouteMeta` 的新标记。这些不引用插件路径，放前面不破坏构建；放后面会让
     中间提交出现「插件用了还不存在的契约」，历史读起来是倒着写的。
     判据：`git grep` 插件目录里对该能力的引用，命中就是前置。查 prop 要两种写法都搜——
     Vue 模板传的是 kebab-case（`default-bold`），只搜 camelCase 的声明名会误判成「没有调用方」。
   - **不引用插件路径的父仓库提交（构建配置修复、文档、工具）位置自由**，通常放在指针提交之后，
     避免打断「子仓库 → 指针」这段不能分离的序列。
   最终顺序形态：宿主前置能力 → 子仓库 → 指针 → 其余父仓库 → 文档。
6. **拆分前先问：被拆出去的这部分，历史上单独存在过吗？**
   - 既有模块新增的能力 → 可以单独成笔（该模块有历史，能力是新叠加的）。
   - 全新模块 → 整体一笔。它从未提交过，任何「基线 / 增量」边界都是现任编排的事后切分。
   - 依据不足时宁可少拆。一次大提交可以接受，一段假历史不能。

## 步骤 4：写提交信息

- 标题`type(scope): 中文摘要`，约 50 字内，不带句号。
- 正文一到两段，讲**为什么做这件事**、以及看 diff 看不出来的**副作用 / 前提条件**。
- **不要**把实现细节搬进正文：改了哪些接口签名、列了哪几列、几个错误码、几条单测用例名、
  逐条文件清单——这些看 diff 就有，写进提交信息只是重复噪声。
- 判断标准：这段文字，半年后看日志的人需不需要？需要 = 留；只有 reviewer 想核对实现 = 删。
- 指针提交：标题点明插件名，正文写`旧 SHA → 新 SHA`、子仓库带入的提交标题、推送顺序。
- 部署前置条件与失败关闭行为写进正文，不要只留在对话里。

正反例（同一个改动）：

```
# 太细：把 diff 复述了一遍
- GET /contacts/employees：姓名/工号关键词、租户、在职、飞书绑定四类过滤与分页全部在 SQL；
  larkBound 走 EXISTS(id_source='own') 子查询；当前页身份一次批量装配
- 新增 5 个单测：正常返回、两种错误码映射、其他错误不误判为未找到、缺 open_id、空入参

# 合适：说清为什么、边界在哪
后台花名册默认只读：姓名、工号、租户、在职状态由 Moka 同步维护，可编辑的只有同步
从不写入的飞书身份与关联后台账号。不提供新增与删除——手造员工没有工号锚点，
删掉的下轮同步又会回来。
```

## 步骤 5：输出命令

每个提交输出**一行**命令：`git add`（或直接 path-limited `commit`）、带`-m`的`git commit`，最后统一附推送。
跨行输出在 PowerShell 里会碎成多条命令——`\` 是 bash 续行符，不是 PowerShell 的；PowerShell 用反引号且行尾不得有空格。
**一律给单行**，不要让用户处理续行。

`-m`必须写在`--`之前：`--`之后的所有内容都被当成路径，`commit -- <paths> -m "..."`里的`-m`会被当作文件名。

子仓库有其它已暂存内容时，path-limited 提交必须带`-- <paths>`：`git commit <paths>`只提交点名路径、
绕过索引里其余已暂存项；漏掉`--`会把别人的暂存内容一并提交。

取`SHA`用 PowerShell 语法——注意**不是**`$OLD=$(git ...)`，PowerShell 里`$( )`是子表达式，
`$(git ...)`整体会被当成一个命令名，直接报`CommandNotFoundException`：

```powershell
$OLD = (git -C apps/lina-plugins rev-parse --short HEAD~2).Trim()
$NEW = (git -C apps/lina-plugins rev-parse --short HEAD).Trim()
```

变量只能在**双引号**字符串里插值，所以带指针 SHA 的`-m`必须用双引号，其它段落用单引号或双引号皆可：

```powershell
git add apps/lina-plugins; git commit -m "feat(linapro-employee-core): 接入插件，前移子仓库指针 $OLD → $NEW" -m '其它正文'
```

输出方案时**先让用户看到变量的值**（`$OLD; $NEW` 或直接给字面 SHA），再给命令——PowerShell 变量在
粘贴后若跨了 shell 会话就丢了，字面值永远可用。提交后用`git show --stat --oneline HEAD`核对落盘文件范围。

**`-C`的参数是相对当前目录的，不是相对仓库根。** 用户在别处执行时`git -C apps/lina-plugins ...`会报
`cannot change to 'apps/lina-plugins': No such file or directory`。凡是给命令，开头先落位：
`Set-Location E:\project\linapro`，或用绝对路径`git -C "E:\project\linapro\apps\lina-plugins"`。
父仓库的`git add`/`git commit`同样要求当前目录是仓库根，不要假设用户停在那里。

## 步骤 6：推送

```powershell
git -C apps/lina-plugins push origin main   # 先子仓库
git push origin main                        # 再父仓库
```

顺序反了会让远端指针指向不存在的`SHA`，别人`git submodule update`时报`not our ref`。

## 附录：各 shell 命令差异

| 场景 | PowerShell | cmd.exe | Git Bash |
|---|---|---|---|
| 删除目录 | `Remove-Item -Recurse -Force dir` | `rmdir /s /q dir` | `rm -rf dir` |
| 取变量 | `$OLD = (git rev-parse --short HEAD~1).Trim()` | `for /f %i in ('git rev-parse --short HEAD~1') do set OLD=%i` | `OLD=$(git rev-parse --short HEAD~1)` |
| 变量插值 | `"... $OLD ..."` | `"... %OLD% ..."` | `"... $OLD ..."` |
| 续行 | 行尾反引号 | 行尾`^` | 行尾`\` |

多行正文始终用多个`-m`，不要用含换行的单个字符串：三种 shell 的引号与续行规则不同，`-m`分段最稳且可整段粘贴。

`core.autocrlf=input`且`.gitattributes`已把`*.sh`、`*.go`、`*.yaml`固定为`LF`，无需额外处理换行。

## 检查清单

提交前逐项确认，任一项不满足就停下来问用户：

- [ ] 范围按任务主题判定，父仓库与子仓库都已取到，未擅自扩到整仓
- [ ] 没有越过仓库根：「全仓」只含本仓与 `apps/lina-plugins`，未用`find`/`ls`扫上级目录的其它仓库
- [ ] 跨窗口的任务改动已通过变更文档与主题关键词补齐，没有按窗口记忆裁剪
- [ ] 被排除的无关改动已向用户复述，未被静默忽略
- [ ] 每个提交只含一个意图，且能独立构建
- [ ] 子仓库提交用`-- <path>`限定，不误带其它暂存内容
- [ ] 无运行时日志、无真实密钥、无构建产物
- [ ] 指针提交的`SHA`来自实际子仓库提交
- [ ] 提交信息内联`-m`，可直接粘贴
- [ ] 每条命令都以`Set-Location`或绝对路径落位，没有依赖用户当前所在的目录
- [ ] 推送顺序：子仓库 → 父仓库
